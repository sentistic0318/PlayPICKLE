# PlayPICKLE

A JavaScript React Native app built in this existing Expo SDK 57 / Expo Router project. Supabase stores accounts, clubs, reservations, doubles tournaments, rankings, notifications, disputes, and audit records. Payments happen directly with the club.

The app never substitutes demo records when Supabase is unavailable. With no configuration it shows a connection prerequisite.

## Start here

Use Node 22.13 or newer (Node 24 works), then open a terminal inside `my-blank-app`:

```powershell
npm install
Copy-Item .env.example .env
```

Fill in only these **public** values in `.env`:

```dotenv
EXPO_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
EXPO_PUBLIC_DEFAULT_AREA=Your city
EXPO_PUBLIC_EAS_PROJECT_ID=YOUR_EAS_PROJECT_ID
```

Find the URL and publishable key in your Supabase project's Connect dialog. Never put a service-role/secret key in this file, app code, or Git. The default area is optional; players can always choose an area manually. Location permission is not needed.

Restart Expo after changing environment values:

```powershell
npm start
npm run web
```

Expo Go is useful for ordinary screen development. Use a development build for reliable app-scheme email links and remote push.

## Set up Supabase

1. Create a Supabase project in your own account.
2. Install the Supabase CLI using its official installation guide, then authenticate.
3. Link and apply the version-controlled migrations:

```powershell
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push
```

Alternatively, run each complete migration in the Supabase SQL editor in filename order. Never apply a partially edited migration. The sequence creates core tables/permissions, competition logic, and the push queue.

For local Supabase, install Docker Desktop and run `supabase start`, then `supabase db reset`. Development seeding is disabled by default. Use the local API URL/publishable key reported by the CLI in `.env`; a physical phone needs your computer's LAN address instead of localhost.

The app depends on the schema and RPCs in these migrations. It does not need an extra custom API server. Row Level Security and checked SQL functions protect mutations; UI visibility is only a convenience.

## Email sign-up and password recovery

In Supabase Authentication → URL Configuration:

- Set the Site URL to your web development URL (normally `http://localhost:8081`) or your eventual deployed web URL.
- Allow `playpickle://auth/callback` and `http://localhost:8081/auth/callback`.
- Add your actual deployed web callback before using it.
- Keep email confirmation enabled if you want verified-email registration.
- Configure a production SMTP sender before inviting real users; Supabase development email limits still apply.

Sign-up and recovery use Supabase's standard email templates and the configured redirect. PKCE codes are exchanged on the device that initiated the flow. The callback also supports token-hash verification and implicit token links. Expired/invalid links show an error. Request a fresh reset from the sign-in page.

Use a development build for the custom `playpickle://` scheme. Expo Go uses a different development URL; allow the exact URL it generates only for development. Test the recovery flow on both mobile platforms before launch.

## Create the first administrator safely

Register your own account, verify its email, and sign in once. In the **trusted Supabase SQL editor**, replace the email below:

```sql
insert into public.administrators (user_id)
select id from auth.users
where lower(email) = lower('your-verified-email@example.com')
  and email_confirmed_at is not null
on conflict (user_id) do nothing;
```

Confirm one intended account was added. Sign out and back in. The Profile screen now exposes platform administration. Never add a profile field or mobile endpoint that grants administrator status.

Administrators can verify club applications, suspend/reactivate accounts, configure ranking policies, and resolve disputes. Owners apply for clubs through Profile → club application. Staff invitations are tied to an email address and limited to the specified club permissions.

## Configure competition policy before publishing

The owner confirmed one game to 11, win by 2. The placement points and dispute window remain unconfirmed. No confirmed policy is silently seeded.

Proposed app-specific policy, pending confirmation: champion 100 points, runner-up 60, semifinalists 30, other entrants 10; both partners receive the placement award; 48-hour reporting window; an administrator resolves disputes.

The administrator must explicitly confirm a ranking/scoring policy before an event is published. Published events preserve their policy snapshot. These are PlayPICKLE competition points, not an external skill rating.

Current scoring stores a single game per match. Set the winning target to 11 or 15 and win-by to 2. Best-of-three scoring requires a game-level schema/UI extension and is not silently represented as a single score.

Accepted teams contain two distinct active players. Registration closes at the deadline; entries lock when the bracket is generated. Unaccepted teams do not enter the bracket. Withdrawals are handled before locking. Club staff schedule matches and submit/verify results through the workspace.

Corrections require a reason and an audit entry. A correction that would rewrite a later match already started or completed is blocked for authorized review. Open disputes hold point finalization. Seasons are archived, not deleted.

## Try each role

Use separate accounts or browser profiles.

1. **Administrator:** verify an owner's club, create/confirm a policy, and review reports.
2. **Owner:** apply for a club; add its time zone, courts, hours, reference prices and cancellation notice; invite staff; configure a season and publish a tournament.
3. **Staff:** accept the invitation from Profile. Check that only granted sections/actions are available. Try another club and confirm the database denies access.
4. **Player:** finish your profile, browse an area, reserve a slot, cancel within policy, and check your inbox/history.
5. **Doubles partners:** each completes a profile. One searches for the other by display name and registers a team. The partner accepts from the tournament page.
6. **Competition:** after the registration deadline, generate a bracket, schedule matches, submit and verify scores, and inspect winner advancement. Submit a participant result report; resolve it as an administrator before finalizing points.

Court times display in the club's IANA time zone. Management forms require a timestamp with its UTC offset, for example `2026-10-15T09:00+08:00`. The database checks actual UTC instants and local opening hours. Courts do not support an opening interval that crosses midnight; split overnight operations into appropriate days when extending that policy.

## Notifications and push delivery

In-app notifications are created by trusted database operations and remain in the player's inbox. Realtime refreshes relevant records; pull to refresh is also available.

Remote push needs extra setup:

1. Create/link an Expo EAS project with `npx eas-cli init`; set your own unique Android package and iOS bundle identifier in `app.json`.
2. Put the resulting project ID in `EXPO_PUBLIC_EAS_PROJECT_ID` and build the app.
3. Configure Android FCM v1 and iOS APNs credentials in EAS.
4. Set a long random **server-only** `PUSH_WORKER_SECRET` for Supabase Edge Functions. Set `EXPO_ACCESS_TOKEN` only if your Expo project enables push access-token security.
5. Deploy `supabase functions deploy push-dispatch`. This endpoint uses its own bearer secret; `verify_jwt=false` does not make it public because the function rejects missing/wrong secrets.
6. Schedule an HTTPS POST to `https://YOUR_PROJECT.supabase.co/functions/v1/push-dispatch` about once a minute, with `Authorization: Bearer YOUR_PUSH_WORKER_SECRET`. Use Supabase Cron/Vault or another trusted scheduler. Do not put the secret in the client or a committed cron script.

The worker claims jobs with expiring leases, retries transient errors, polls Expo receipts, and disables unregistered device tokens. Push is best-effort and may repeat after an ambiguous transport failure; the unique in-app notification is the authoritative record. A push ticket means Expo accepted the request, not that a person read it. Lock-screen text is deliberately generic.

Users who deny permission still receive in-app updates. Push delivery cannot be verified without a device build and credentials.
